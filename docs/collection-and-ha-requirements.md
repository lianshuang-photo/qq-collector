# QQ 群消息采集与高可用需求

## 背景

QQ 官方机器人无法读取加入机器人之前的普通群历史消息，也没有可靠的普通群历史补拉接口。因此服务的首要目标是从机器人在线后开始，持续接收群消息并落盘，尽量缩短断线窗口。

当前项目定位是**消息采集和持久化服务**，不是 issue 自动整理系统。消息、附件和清理传输凭据后的事件 JSON 作为后续社区反馈工作的原始材料。

## 已完成的基础能力

- 通过官方 WebSocket 接收 `GROUP_MESSAGE_CREATE` 和 `GROUP_AT_MESSAGE_CREATE`。
- 自动发现入群的群并查询群资料和机器人接收状态。
- SQLite WAL 数据库保存群、消息、附件、事件和恢复状态。
- 消息按 `(group_openid, message_id)` 去重；在同一事务中保存消息并推进 `seq`。
- 图片和语音自动下载；视频、普通文件和过大媒体只留元数据。
- 访问令牌自动刷新、心跳、Resume、指数退避重连。
- macOS LaunchAgent 自动启动和异常拉起。

## 多设备稳定性要求（设计目标，尚未实现）

### 连接原则

本实现使用 `shard=[0,1]`；部署时需要核验网关返回的分片和会话限制，同一时刻只运行一个采集实例。禁止多个设备同时用同一套 Bot 凭证连接来做“并行采集”；这会造成会话互相挤下线，反而增加丢消息概率。

发送消息的 REST 请求可以来自其他设备，但不能因此启动第二个长期 WebSocket 采集器。

### 推荐的主备模式

```text
主采集器 ── 唯一 WebSocket ── QQ Gateway
    │
    ├── 持久化消息和附件
    ├── 保存 session_id / seq
    └── 暴露心跳和进程状态

备用采集器 ── 平时不连接 QQ
    └── 主租约过期后接管并尝试 Resume
```

要求：

1. 主采集器持有带过期时间的租约；租约由 Redis、PostgreSQL 或其他可跨主机访问的协调存储提供。
2. 备用采集器只有在租约确认过期后才能连接，必须避免双主。
3. 接管前先读取最近的 `session_id` 和 `seq`，发送 Resume；Resume 失败再重新 Identify。
4. 所有实例使用同一个可靠的持久化数据库。SQLite 文件不能直接放在普通网络共享盘上作为多机并发数据库；跨机器主备应迁移到 PostgreSQL 等服务端数据库，或明确规定只有主机写 SQLite、备用机只在接管后使用本地完整副本。
5. 记录连接断开、Resume 成功/失败、Identify、token 刷新和租约变更，并配置告警。
6. 任何设备全部离线期间仍可能丢消息，因为 QQ 普通群没有历史消息补拉能力；主备只能缩短故障窗口，不能提供历史回放保证。

### 稳定性指标

第一阶段建议：

- 主采集器单 WebSocket 在线率 ≥ 99%。
- 心跳 ACK 超时 1 个周期内主动断开并重连。
- 断线后 30 秒内开始重连，退避上限 5 分钟。
- 进程重启后能读回数据库中的 `session_id`、`seq` 和消息记录。
- 消息落库成功后才推进恢复序号，避免数据库写失败却丢失恢复位置。
- 每日 SQLite 一致性备份；迁移到 PostgreSQL 后使用数据库备份策略。

## 后续迭代顺序

1. 保持当前单机单连接部署，增加心跳过期告警和磁盘空间告警。
2. 为出站消息增加 `outbound_messages` 表和幂等键，记录欢迎语/管理员消息的发送结果。
3. 做一个不连接 QQ 的备用进程，只负责监控和接管，不做同时连接。
4. 有明确跨机器需求后迁移到 PostgreSQL，再实现租约和主备切换。
5. 最后再考虑消息检索、反馈标记和 issue 整理；不在采集服务里混入自动分类逻辑。

## 验收标准（含未来主备能力目标）

- 在已开启“获取群内全部消息”的群内发消息，5 秒内能在数据库查询到。
- 重复事件不会产生重复消息。
- 图片在临时 URL 过期前进入本地文件，并可用 SHA-256 校验。
- 主动断开主进程后，LaunchAgent 或备用实例能够恢复连接。
- 同时启动两个采集器时必须被租约/进程锁阻止，不能静默形成双连接。
- 离线期间的不可恢复消息要在运行状态中明确记录，不能声称已补齐。
